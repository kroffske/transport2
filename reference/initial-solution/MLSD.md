# ML System Design: раннее прогнозирование задержек транспорта

## 1. Решение и границы задачи

Основная модель предсказывает **знаковую задержку на заданном будущем остановочном событии**.
Для конкурсного CSV нужен регрессионный прогноз, а для диспетчера — отдельные вероятность
опоздания, интервал неопределенности, свежесть данных и диагностические паттерны.

Не строить LLM/RAG в роли численного предиктора. Не начинать с большого Transformer,
дорожного симулятора или what-if без надежной разметки. Сначала контракт данных,
валидный baseline и честная временная проверка; затем дополнительная сложность.

Цель MVP — превзойти простые baseline по MAE и воспроизводимо выдавать API-прогноз.
Цель эксплуатационного решения существенно строже: обнаруживать **новые** инциденты
заранее, не перегружать диспетчера ложными тревогами и не скрывать потерю связи.
Текущий baseline достигает первой цели на проведенной диагностике, но еще не второй.

## 2. Формальная постановка

Единица наблюдения: `(sample_id, tr_id, T, target_stop_id)`.

```text
s* = первое плановое остановочное событие ТС с временем в (T+600, T+900]
y  = actual_arrival(s*) - planned_arrival(s*)
X  = known_point_fields + telemetry_at_or_before(T) + known_schedule_plan
```

В раздаче s* и его planned time уже указаны. `target_stop_id` равен ID планового
прибытия `tt_action_item_id`, а не постоянному идентификатору физической остановки.

Регрессионный выход — `prediction_s`, включая отрицательные значения.
Прибавление к `target_time_begin` дает оценку фактического прибытия.
Бинарный выход `p_late = P(y > 120 | X)`; раннее отправление/прибытие `y < -60`
может стать отдельной вероятностной головой, но не смешивается с опозданием.

**Не подменять задачи:** горизонт 10–15 минут в разметке относится к плану.
Время до фактического прибытия равно `horizon_s + y` и не обязано попадать в это окно.
В test 88/353 фактических lead time выходят за (600, 900] секунд.
Момент «начала задержки» должен быть определен отдельно: прибытие с опозданием,
первое превышение порога lateness или начало эпизода нарушения интервала — разные события.

Прокси нового опоздания: `cur_dev_s <= 120` при `target_delay_s > 120`.
Это проверяет возникновение опоздания относительно последней известной остановки,
но не является полной разметкой начала инцидента.

## 3. Источники и контракт доступности

### Источники

`labels_train` — supervised targets; `labels_test` — локальная диагностика.
`traffic.csv` — уже декодированная навигация; `schedule` — план плюс факт для аудита.
`validate/points.csv` и validate-входы — только для финального scoring.
Ни target, ни target_class, ни будущий факт, ни служебные поля ручной разметки
не попадают в признаки.

Приложение содержит только 1 141 train-точку с доступным raw context.
Режим `available` явно переиспользует входные данные из test для этих train-точек;
совпадение ID, плана и дат проверено. Столбцы факта удаляются allowlist еще при чтении.
3293 точки без сырого контекста исключаются только из context-эксперимента.
Отдельная core-модель использует все 4434 train-точки без телеметрии.
Это разные обучающие популяции, а не чистая абляция влияния GPS.

### Point-in-time правила

Для соревнования: `event_time <= T`. Для эксплуатационного replay:
`event_time <= T AND receive_time <= T`; выбранная политика входит в артефакт модели.
Поступившие позже исправления фильтруются **до** дедупликации.
Не использовать `bfill`, centered rolling, интерполяцию с будущими координатами,
статистики целого дня или target encoding по всем фолдам.

План на будущую остановку допустим, когда он действительно опубликован к T.
В производстве нужны `schedule_version` и время доступности версии; в раздаче они отсутствуют.
Подсказка cur_dev_s разрешена организаторами, но онлайн ее должен вычислять Backend
по уже подтвержденным прохождениям остановок, а не получать из будущего расписания.
Для эксплуатации добавить `cur_dev_is_known`, `cur_dev_age_s`, источник и доверие к маппингу.
Отсутствие информации не должно автоматически означать отклонение 0 секунд.

Время CSV не содержит timezone. В текущем коде шкала сохраняется без преобразования.
Unix timestamp NDTP нужно явно привести к согласованной шкале; timezone пользователя
или системный datetime.now() не определяют время исторического replay.

## 4. Архитектура и граница команд

```text
OFFLINE
labels + traffic + schedule PLAN
             ↓
   audit / data contract
             ↓
   shared FeatureBuilder
             ↓
 fit → tune → calibration → future audit
             ↓
 CatBoost + GRU + risk calibrator + quantiles
             ↓
 model files + schema + metrics + split/source manifests

ONLINE
NDTP TCP stream / historical replay
             ↓
 BACKEND: decode → validate → device→vehicle → event-time state
             ↓
 current point + past telemetry + versioned schedule PLAN
             ↓
 ML SERVICE: same features → models → quality status
             ↓
 BACKEND: alert policy → deduplication/cooldown → event log
             ↓
 DISPATCHER: map, risk, ETA, uncertainty, freshness, evidence
```

Backend владеет TCP, очередями, аутентификацией, потоковым состоянием,
идентификацией рейса, подбором целевой остановки, накоплением инцидентов и BI API.
ML-модуль владеет версией признаков, обучением, инференсом, калибровкой, оценкой.

Для hackathon MVP достаточно двух сервисов и Redis-состояния по ТС;
не обязательно добавлять Kafka, отдельный feature store и сложный оркестратор.
Долговременное сырое хранение и immutable prediction log нужны для replay/аудита.
Разделить модель, которую валидировали, и модель, которую потом переобучили.

### Вход ML API

Точка: sample_id, tr_id, T, target_stop_id, target_time_begin, cur_dev_s.
Контекст: навигация за последние 15 минут и плановые остановки текущего рейса.
Потоковые unit_id и tr_id не обязаны совпадать: необходим реестр соответствия.

### Выход

Задержка в секундах, прогноз прибытия, p_late, q10/q90, статус качества,
возраст последнего пакета, диагностический паттерн, версия схемы/модели.
`status=degraded` не превращается в «зеленый риск».
Ни вероятность, ни SHAP-вклад сами по себе не являются доказательством причины.

## 5. Признаки

В реализованной версии 85 табличных признаков с контекстом.

| Группа | Реализовано | Следующее улучшение |
|---|---|---|
| Состояние | cur_dev_s, abs(cur_dev_s), горизонт | возраст отклонения, тренд последних подтвержденных остановок |
| Время | sin/cos времени суток, день недели | дополнительные дни; календарь нельзя оценить на одном дне |
| Движение | mean/std/min/max/q10/q90 скорости за 1/3/5/10/15 мин | time-weighted скорости и более надежные acceleration/turning |
| Простои | доля speed<2, длина последнего непрерывного простоя | геозона остановки, двери после появления соответствующих данных |
| Качество | число пакетов, валидность, age, gap, span, missing flags | late-arrival/clock skew и confidence map matching |
| План | целевая геометрия, плановый интервал, число остановок впереди | рейс, направление и версия маршрута |
| Пространство | дистанция до цели и плановой позиции, очищенный путь | map matching вдоль реальной геометрии дороги |

Скорость выше 120 км/ч в baseline превращается в missing: это явный sanity-порог,
а не утверждение о нормативной скорости транспорта. Координаты invalid не становятся (0,0).
Из наличия speed=0 без дверей нельзя делать вывод «длительная посадка».

Текущая линейная интерполяция между плановыми остановками — приближение для признаков,
**не** полноценный дорожный map matching. Нужны route shapes/direction, candidate segments,
согласование курса, непрерывности движения и пройденного расстояния.
Без route_id нельзя уверенно выдавать качество «по маршрутам»; пока доступен разрез по ТС.

## 6. Модели и обучение

Сравнить на одном tune-блоке нулевой прогноз, cur_dev_s и медиану обучающей части.
Медиану нельзя считать по test. Затем:

**CatBoost direct:** обучать y с MAE.
**CatBoost residual:** обучать `y - cur_dev_s`, возвращать `cur_dev_s + correction`.
Residual-постановка — проверяемая гипотеза, а не гарантированный выигрыш.
В baseline используется depth=5, l2_leaf_reg=8, learning_rate=0.04, максимум 500 деревьев,
early stopping на tune. Исследовательский бюджет можно изменить CLI.

**PyTorch GRU:** 60 временных шагов по 15 секунд, 9 каналов, hidden=24;
табличная ветка и residual-голова. Последовательность собирается backward-asof,
с масками и ограничением удержания старой точки 60 сек. L1Loss, AdamW,
gradient clipping, ранняя остановка на tune. Табличный scaler обучается только на fit.
Большой Transformer при таком числе реальных размеченных точек не является первым приоритетом.

**Ансамбль:** вес GRU выбирается из небольшой фиксированной сетки на tune.
В сохраненном эксперименте выбран 0.25 GRU + 0.75 residual CatBoost.
Не выбирать вес по test, не усреднять модели только ради наличия PyTorch в схеме.
Для серьезного stacking нужны out-of-fold предсказания без доступа к целям того же фолда.

**Вероятность:** независимый CatBoostClassifier для y>120 с Logloss;
sigmoid/Platt-калибровка на отдельном временном calibration-блоке.
Не преобразовывать задержку в вероятность через произвольную сигмоиду.
Перевзвешивание классов и focal loss могут сдвигать вероятности — после них особенно важна калибровка.

**Неопределенность:** CatBoost q10/q90 с Quantile loss. Исправление crossing не гарантирует
80% покрытия; отдельно измеряются coverage и средняя ширина. При появлении данных
возможна временная conformal-калибровка, с проверкой устойчивости при дрейфе.

## 7. Валидация

В реальной части практически один день и одни и те же 13 ТС. Random train_test_split
переоценивает независимость соседних точек. Название labels_test не устраняет эту проблему.

В реализации: 4 блока по времени. Для context-эксперимента:

| Блок | T | Строк после purge |
|---|---|---:|
| fit | 02:10–13:40, 06.01.2026 | 670 |
| tune | 14:10–16:55 | 186 |
| calibration | 17:25–20:10 | 102 |
| audit | 20:40–23:55 | 112 |

Точный состав: artifacts/context/split_manifest.csv.
Граничное правило консервативно:

```python
label_ready = target_time_begin + max(target_delay_s, 0)
keep_training_row = label_ready < next_block_start - timedelta(minutes=15)
```

Так исход следующей остановки уже известен до окна признаков следующего блока.
Факт используется здесь только для определения зрелости метки, не как признак.
Простой gap=15 в TimeSeriesSplit означает 15 СТРОК, а не минут;
для нескольких ТС и нерегулярных времен нужен timestamp-based gap.

Следующий уровень: несколько rolling-origin окон; проверка на следующем дне/неделе;
отдельный holdout новых ТС/маршрутов. Группировать одинаковые target events и реальные рейсы.
Синтетические варианты одного родительского рейса нельзя разнести по разные фолды;
без provenance синтетики ее оценка не доказывает перенос на реальные данные.

После просмотра audit не использовать его для бесконечного подбора. Последующие
эксперименты проверять на новом окне; даже «маленькая поправка порога» является подбором.
Для финального refit фиксировать структуру, число деревьев/эпох и ансамбль заранее;
калибратор нельзя без проверки переносить на заново обученный классификатор.

## 8. Метрики и правила приемки

### Соревнование

`MAE = mean(abs(y - prediction))`, секунды, меньше лучше.
Сохранять RMSE, P95 абсолютной ошибки, signed bias, долю ошибок <=30/60 с,
MAE отдельно late/early/ontime и macro-MAE по ТС.
MAE опозданий нельзя скрывать хорошим средним результатом на штатных поездках.
MAPE не выбирать: у цели есть нули и отрицательные значения.
Нормализованный score нельзя воспроизвести без MAE_TARGET; не выдумывать значение константы.

### Вероятности

Average Precision — основная метрика ранжирования; ROC-AUC — дополнительная.
AP не тождествен трапецеидальной площади под PR-кривой.
Brier и Logloss оценивают качество вероятностей; Brier не является исключительно
мерой калибровки, поэтому дополнительно нужна reliability diagram.
При выборе red threshold оптимизировать recall при согласованной precision/нагрузке.
В примере precision>=0.8 — цель НА CALIBRATION, не гарантия на audit.

### Ранние предупреждения

Обязательно отдельно оценивать случаи `cur_dev_s <= 120`, чтобы модель не побеждала,
повторяя «ТС уже опаздывает». Прокси point-recall текущего baseline: 0 из 11 новых
опозданий в audit при выбранном пороге. Это блокер для заявления о готовности раннего алерта.
Следующее исследование — отдельная модель/голова onset-risk и порог для этой подгруппы,
не смешанный с предупреждениями о продолжении уже известной задержки.

После определения события считать:

```text
EventRecall@10–15 = incidents with at least one valid alert 10–15 min before onset
                   / all eligible incidents
FalseAlertsPerVehicleHour = unmatched deduplicated alert episodes
                            / actually observed vehicle-hours
LeadTime = true onset - first valid alert
```

Повторные алерты одного эпизода не увеличивают TP. Нужны cooldown/hysteresis,
сопоставление алерт↔инцидент, наблюдаемая длительность работы, признаки закрытия события.
Не заменять vehicle-hours разницей между первым и последним пакетом при длинных обрывах связи.
Не заявлять event-recall по имеющимся point labels без дополнительной разметки.

### Инженерные и продуктовые метрики

Измерять P50/P95/P99 от получения пакета до алерта, throughput, долю устаревших
прогнозов, fallback rate, потерянные/дублирующиеся пакеты, время восстановления связи.
Начальные проектные SLO: ML P95<100 мс для одного прогноза, end-to-end P95<1 с
при согласованной нагрузке. Это цели, не измеренные гарантии.
Текущий замер ~14 мс P95 относится только к моделям, без feature building и сети.

Продуктово: доля полезных подтвержденных алертов, время реакции диспетчера,
доля своевременно обнаруженных инцидентов и количество ложных тревог.
Снижение реальных задержек после вмешательств требует отдельного дизайна эксперимента;
MAE на истории не доказывает операционный эффект.

## 9. Отказы, объяснения, мониторинг

Старые/отсутствующие GPS → core fallback с quality warning; без core → cur_dev baseline
без уверенной вероятности. Расписание не найдено → неизвестный mapping, не выдуманный участок.
При недоступности ML Backend показывает последний прогноз с возрастом/TTL, а не как свежий.

Причины формулировать как наблюдаемые паттерны: «скорость снизилась», «долгий простой»,
«опоздание уже было на предыдущей остановке», «недостоверная навигация».
Не утверждать ДТП, пробку, посадку или светофор без соответствующих источников.
LLM может перефразировать проверенные показатели и инструкции, но не устанавливает причины.

Логировать: cutoff T, target event, input max event/receive time, freshness, модель/схема,
прогноз, вероятность, алерт, фактический исход после его наступления, действие диспетчера.
Мониторить drift признаков/цели, MAE по подгруппам, калибровку и false-alert budget.
Переобучение запускать после накопления реальных новых исходов; promotion с контрольными
тестами и возможностью rollback. Не адаптировать модель на собственных предсказаниях как на фактах.

What-if про резервный транспорт не выводится из observational-регрессора без модели
вмешательства/симулятора. В MVP допустимы сценарии с явно заданными допущениями,
но не обещания причинного эффекта.

## 10. План реализации по приоритетам

**P0 — данные и submission-контракт.** Получить отсутствующие scoring inputs,
сверить актуальную раздачу, MAE_TARGET, смысл момента события, timezone и допуск
shared train/test context. Критерий готовности: проходящие проверки схемы и честный валидный CSV.

**P1 — воспроизводимый ML baseline.** Уже реализованы core/context модели, временной
split, признаки, CatBoost/GRU, калибровка, интервалы, тесты и сохранение артефактов.
Критерий: улучшение на независимых временных окнах, а не только лидерборде.

**P2 — ранние алерты.** Уточнить onset label, собрать эпизоды, сделать отдельную оценку
новых задержек, настроить budget/пороги на calibration, проверить на новом holdout.
Критерий: полезный event-recall при приемлемых ложных тревогах; текущий baseline этот этап не прошел.

**P3 — replay и интеграция.** Backend реализует NDTP, реестр unit→vehicle,
point generation и состояние; ML API объединяется с BI. По спецификации autoGenerate
эмулятора дает случайную телематику без гарантированного соответствия расписанию:
для осмысленной демонстрации прогноза нужен исторический replay, а не только случайный GPS.

**P4 — упаковка и защита.** Проверить Docker на целевой машине, разрывы связи,
offline/online parity, нагрузку, документацию API и демонстрационный сценарий.
Подготовить обе требуемые версии решения на платформе, не только CSV.

Дополнительные дни, полноценный map matching, neighbor-traffic features,
ONNX/квантование и what-if — после выполнения P0–P4, а не вместо них.
