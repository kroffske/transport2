## recommendations

- До параллельного исполнения определить конкретные owning files для split/evaluator, features/training и submission validator. Сейчас все reusable изменения сходятся в `transport_ml/`; функциональные названия дочерних задач сами по себе не разводят запись. Текущая цепочка dependencies последовательна, поэтому немедленного конфликта нет.
- В handoff ML → Backend включить происхождение и поведение при отсутствии каждого онлайн-признака, особенно `cur_dev_s`, соответствие `tr_id` эмулятору и вычисление target stop. Не принимать input schema за доказательство доступности значений на потоке.
- В baseline verification явно сохранить тесты поздних пакетов/исправлений и порядка cutoff → dedup. Одного `event_time <= T` недостаточно для утверждения доступности в реально принятом к T потоке; официальный CSV-контракт и received-time sensitivity стоит сообщать отдельно.
- В data-audit проверять схемы и row counts у CSV, а у README, спецификации и Docker tar — комплектность и соответствующий формат. Формулировка «Row counts и schemas для всех 13 файлов» сейчас смешивает разные типы входов.
- «Высокая/средняя выполнимость» в scorecard обозначить как предварительную оценку возможности выполнить работы. Это не подтверждённая вероятность получить максимум баллов. `MAE_TARGET` в README не задан; локальные MAE и заявленные источником ≈0.40 не заменяют score платформы.
- Сделать T-3/T-4 в roadmap и scorecard ссылками на реальные `task.md`. Перед моделированием baseline-владелец должен определить сравниваемый hurdle, допустимый tolerance и конкретный бюджет эксперимента; это можно решить по результатам data-audit без дополнительного человеческого согласования.
