# Географическая основа будущей карты Москвы

Для текущей интеграции достаточно передавать реальные координаты ТС и плановых остановочных прибытий. Three.js в будущем будет рисовать эти данные; он не предоставляет карту, дороги или маршруты.

## Что действительно есть

Проверка CSV 2026-09-26: validate и test содержат по 5 558 плановых прибытий, 13 ТС и 847 уникальных `geom`; train — 16 674 прибытия, 39 ТС с синтетикой и те же 847 уникальных координат. Пропусков координат schedule не найдено. Bounding box: lon 37.148758–37.86591669, lat 55.51808043–55.98421642. Это покрытие конкретной выборки, не всей Москвы.

`unit_id → tr_id` восстанавливается из traffic: конфликтов внутри каждого split не найдено; runtime всё равно загружает явную таблицу и проверяет конфликт при старте. Связь ТС с остановочным прибытием — `(tr_id, tt_action_item_id)`; `target_stop_id` обозначает это прибытие. Совпадение координат помогает группировать точки для рисунка, но не создаёт надёжного ID физической остановки, направления или маршрута.

В schedule нет `route_id`, `trip_id`, shape дороги или устойчивого stop ID. В traffic есть lon/lat, скорость км/ч и heading в градусах. Высоту не использовать как точную высоту поверхности: её datum/качество не установлены. Последовательность plan для ТС полезна для сопоставления по времени, но линии между остановками не повторяют дорожную сеть. Существующий motion-v1 прямо обозначает такую геометрию как упрощение, не map matching.

## Решение для контракта

- Backend отдаёт `lon`, `lat` в градусах WGS84, в JSON/GeoJSON порядок `[longitude, latitude]`; `location_valid`, event/receive time и freshness обязательны. Не смешивать метры с градусами. Исходный dataset не указывает EPSG явно: WGS84 — рабочая гипотеза совместимости GPS/NDTP, проверить при подключении внешней геометрии.
- Будущая сцена переводит WGS84 через geocentric в local ENU относительно фиксированного origin `lon=37.6173, lat=55.7558, ellipsoidal_height=0`. Единица — метр; Three.js `x=east`, `y=up`, `z=-north`. Преобразование и origin version должны быть едиными для дорог, ТС и остановок. Это выбранный контракт проекта; [PROJ описывает topocentric ENU и предварительное geodetic→geocentric преобразование](https://proj.org/en/stable/operations/conversions/topocentric.html).
- Для первой плоской карты считать unknown height равной display-height 0 с соответствующей пометкой; не выдавать её за измерение. На масштабе города плоское представление имеет искажения; перед будущим внедрением проверить контрольные точки и расстояния на краях bbox. Точное расстояние для модели продолжает рассчитываться геодезически, независимо от scene coordinates.
- Web Mercator допускается на границе будущего tile-renderer, но не подменяет метры ENU или физические расстояния модели. Сцену сейчас не строить и runtime-зависимости PROJ/Three.js только ради документа не добавлять.

## Откуда брать недостающие данные

Выбранный кандидат для фоновых дорог и зданий — выгрузка OpenStreetMap нужного bbox/региона либо провайдер на этих данных. OSM распространяет данные по ODbL: нужны атрибуция и соблюдение условий лицензии при распространении производной базы. Конкретный будущий пакет проверяется до распространения. [Первичный источник — OSM copyright](https://www.openstreetmap.org/copyright).

Не скачивать город пачкой с публичного raster tile endpoint: политика запрещает bulk/offline prefetch. Для offline demo нужен разрешённый data extract и собственный renderer либо провайдер с подходящими условиями. [Первичный источник — OSM tile policy](https://operations.osmfoundation.org/policies/tiles/).

Для точных транспортных маршрутов нужны operator route/trip/stop IDs и shapes либо проверенные OSM route relations. Наличие полного актуального набора маршрутов Москвы в конкретном внешнем источнике здесь не установлено. Нельзя получить правильную нитку маршрута просто кратчайшим путём между GPS-точками. До будущей карты: выбрать и проверить датированный источник, лицензию, полноту bbox/route directions; сопоставить 847 точек с устойчивыми stop IDs вручную проверяемым способом; сохранить unresolved mappings. Если операторский источник недоступен, показывать только GPS и schematic stop sequence с явной подписью.

Эта основа не реализует карту и не закрывает C4. Следующий UI-этап должен отдельно проверить покрытие маршрутов, точность преобразования координат, производительность сцены и понятность отображения диспетчеру.
