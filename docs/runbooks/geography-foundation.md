# Географическая основа карты Москвы

**Статус 2026-09-27 (T-7).** Карта реализована: `dashboard/` рисует 2D-вид сверху на MapLibre с локальным PMTiles-извлечением OSM (`consumer/map/manifest.json`), маркеры ТС и цели — в custom-слое Three.js; см. [`dashboard/README.md`](../../dashboard/README.md). Этот документ остаётся геоконтрактом и списком ограничений. Реальные трассы маршрутов по-прежнему не сопоставлены.

Что сейчас рисуется для выбранного ТС ([Backend v1](../api/backend-v1.md), `GET /v1/route/{tr_id}`):

- ТС — последняя достоверная позиция GPS из NDTP; цель — координата плановой остановки из расписания (`target_lon`, `target_lat` в строке snapshot);
- «путь по GPS прогона» — достоверные GPS-точки окна, которые подаёт драйвер эмулятора (display-only, подпись на экране: не официальная трасса);
- пройденная часть — достоверные GPS-точки, принятые Backend в этом прогоне;
- остановки — плановые прибытия `tr_id` с координатами из расписания. Остановка без координаты или вне bbox карты `37.25,55.50,38.00,56.00` исключается и считается в `stops_dropped`; `(0,0)` не рисуется никогда.

Это и есть вариант «только GPS и плановая последовательность остановок с явной подписью» из раздела ниже; map matching не выполняется.

## Что действительно есть

Проверка CSV 2026-09-26: validate и test содержат по 5 558 плановых прибытий, 13 ТС и 847 уникальных `geom`; train — 16 674 прибытия, 39 ТС с синтетикой и те же 847 уникальных координат. Пропусков координат schedule не найдено. Bounding box: lon 37.148758–37.86591669, lat 55.51808043–55.98421642. Это покрытие конкретной выборки, не всей Москвы.

`unit_id → tr_id` восстанавливается из traffic: конфликтов внутри каждого split не найдено; runtime всё равно загружает явную таблицу и проверяет конфликт при старте. Связь ТС с остановочным прибытием — `(tr_id, tt_action_item_id)`; `target_stop_id` обозначает это прибытие. Совпадение координат помогает группировать точки для рисунка, но не создаёт надёжного ID физической остановки, направления или маршрута.

В schedule нет `route_id`, `trip_id`, shape дороги или устойчивого stop ID. В traffic есть lon/lat, скорость км/ч и heading в градусах. Высоту не использовать как точную высоту поверхности: её datum/качество не установлены. Последовательность plan для ТС полезна для сопоставления по времени, но линии между остановками не повторяют дорожную сеть. Существующий motion-v1 прямо обозначает такую геометрию как упрощение, не map matching.

## Решение для контракта

- Backend отдаёт `lon`, `lat` в градусах WGS84, в JSON/GeoJSON порядок `[longitude, latitude]`; `location_valid`, event/receive time и freshness обязательны. Не смешивать метры с градусами. Исходный dataset не указывает EPSG явно: WGS84 — рабочая гипотеза совместимости GPS/NDTP, проверить при подключении внешней геометрии.
- Реализованная 2D-карта использует Web Mercator MapLibre (`MercatorCoordinate`), а не ENU; ENU ниже — контракт для будущей 3D-сцены. Будущая сцена переводит WGS84 через geocentric в local ENU относительно фиксированного origin `lon=37.6173, lat=55.7558, ellipsoidal_height=0`. Единица — метр; Three.js `x=east`, `y=up`, `z=-north`. Преобразование и origin version должны быть едиными для дорог, ТС и остановок. Это выбранный контракт проекта; [PROJ описывает topocentric ENU и предварительное geodetic→geocentric преобразование](https://proj.org/en/stable/operations/conversions/topocentric.html).
- Для первой плоской карты считать unknown height равной display-height 0 с соответствующей пометкой; не выдавать её за измерение. На масштабе города плоское представление имеет искажения; перед будущим внедрением проверить контрольные точки и расстояния на краях bbox. Точное расстояние для модели продолжает рассчитываться геодезически, независимо от scene coordinates.
- Web Mercator допускается на границе tile-renderer (так работает текущая карта), но не подменяет метры ENU или физические расстояния модели. Зависимость PROJ только ради документа не добавлять.

## Откуда брать недостающие данные

Выбранный кандидат для фоновых дорог и зданий — выгрузка OpenStreetMap нужного bbox/региона либо провайдер на этих данных. OSM распространяет данные по ODbL: нужны атрибуция и соблюдение условий лицензии при распространении производной базы. Текущее извлечение и его атрибуция описаны в `consumer/map/manifest.json`; лицензии поставляемых JS-библиотек — в [`dashboard/README.md`](../../dashboard/README.md#лицензии). [Первичный источник — OSM copyright](https://www.openstreetmap.org/copyright).

Не скачивать город пачкой с публичного raster tile endpoint: политика запрещает bulk/offline prefetch. Для offline demo нужен разрешённый data extract и собственный renderer либо провайдер с подходящими условиями. [Первичный источник — OSM tile policy](https://operations.osmfoundation.org/policies/tiles/).

Для точных транспортных маршрутов нужны operator route/trip/stop IDs и shapes либо проверенные OSM route relations. Наличие полного актуального набора маршрутов Москвы в конкретном внешнем источнике здесь не установлено. Нельзя получить правильную нитку маршрута просто кратчайшим путём между GPS-точками. До показа реальных маршрутов на карте: выбрать и проверить датированный источник, лицензию, полноту bbox/route directions; сопоставить 847 точек с устойчивыми stop IDs вручную проверяемым способом; сохранить unresolved mappings. Если операторский источник недоступен, показывать только GPS и schematic stop sequence с явной подписью.

Документ не закрывает C4. Следующий этап после сопоставления маршрутов должен отдельно проверить покрытие маршрутов, точность преобразования координат, производительность сцены и понятность отображения диспетчеру.
