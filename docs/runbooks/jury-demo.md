# Инструкция для жюри

Основной сценарий: официальный эмулятор NDTP → Backend → ML-ядро → диспетчерский дашборд. Драйвер читает исторические GPS-точки и подаёт их официальному эмулятору; прогнозы рассчитывает модель. Ниже — запуск с нуля и проверка результата. Все команды выполняются из корня клонированного репозитория.

Дашборд — работающий прототип диспетчерской карты с событиями и диагностикой. Полный BI с долговременной аналитикой и серверным хранением действий диспетчера пока не реализован.

## 1. Подготовить файлы и Docker

Нужны Docker с Compose v2, Git и свободные порты `8000`, `8001`, `8002`, `9201`, `18080`. Для первой сборки нужен доступ к реестру Docker и Python-зависимостям. Проверьте Docker:

```bash
docker compose version
docker info
```

Модель `models/final/`, карта `consumer/map/moscow.pmtiles` и собранный интерфейс уже находятся в репозитории. Три файла официальной раздачи организаторов нужно положить вручную:

| Путь в репозитории | Для чего нужен |
|---|---|
| `data/validate/traffic.csv` | GPS-точки и соответствие транспортных средств NDTP-устройствам |
| `data/validate/schedule_plan.csv` | Плановые остановки и время прибытия |
| `data/emulator/ndtp-telemetry-emulator.tar` | Официальный Docker-образ эмулятора |

Эти файлы не хранятся в Git. Размеры и SHA-256 для проверки — в [README](../../README.md#быстрый-путь-для-жюри). Без официальной раздачи свежий clone недостаточен для запуска потока. Фактические прибытия, train/test и локальные файлы обучения `.local/` для демо не нужны.

Загрузите образ один раз и проверьте модель:

```bash
docker load -i data/emulator/ndtp-telemetry-emulator.tar
docker image inspect ndtp-telemetry-emulator:1.0
(cd models/final && shasum -a 256 -c SHA256SUMS)
```

На Linux вместо `shasum -a 256` можно использовать `sha256sum`. Образ эмулятора `linux/amd64`; на Apple Silicon Docker Desktop запускает его через эмуляцию.

Если официальные данные лежат вне репозитория, задайте перед запуском `DATA_DIR` как абсолютный путь к каталогу, содержащему `validate/`. Чтобы сохранить приближённые дорожные формы, скопируйте туда также tracked-файл `data/routes/route_shapes.json` с тем же относительным путём `routes/route_shapes.json`; без него Backend корректно вернётся к прямым отрезкам между остановками. По умолчанию Compose использует `./data` и `./models/final`.

## 2. Запустить официальный эмулятор и три модуля

```bash
SOURCE_COMMIT=$(git describe --always --dirty --abbrev=40) docker compose --profile demo up -d --build --force-recreate --remove-orphans
```

Команда запускает `ml`, `backend`, `consumer`, официальный `emulator` и `driver`. Драйвер сам регистрирует прогон в Backend через `POST /v1/run`, затем отправляет GPS-точки эмулятору через его штатный `POST /api/config`. Эмулятор передаёт NDTP на `backend:9201`. Отдельно запускать sender или вручную конфигурировать эмулятор для этого сценария не требуется.

Проверьте запуск:

```bash
docker compose --profile demo ps
curl -fsS http://localhost:8000/ready
curl -fsS http://localhost:8001/ready
curl -fsS http://localhost:8002/ready
docker compose --profile demo logs --tail=20 driver
```

Ожидается: `ml`, `backend`, `consumer` становятся `healthy`; `/ready` отвечает `status: ready`. Backend возвращает `source_clock: simulation`, затем `run.source: official_emulator`, `run.state: running` и ненулевой `run.accepted_frames`. В логах драйвера появляются `feed_loaded`, `run_registered`, `heartbeat`. До регистрации прогона состояние `waiting_driver` нормально.

По умолчанию показывается окно 6 января 2026 года `06:30–08:30` с ускорением ×5: 1 минута показа соответствует 5 минутам данных, полный прогон длится около 24 минут. Для другого ускорения и окна передайте переменные в ту же команду; допустимые значения и эффект прореживания GPS описаны в [настройках прогона](local-demo.md#настройки-прогона).

В конце окна состояние меняется на `completed`, в логе появляется `run_completed`, контейнер `driver` завершается с кодом 0. Это штатное завершение: остальные сервисы продолжают работать, последний снимок остаётся доступен.

## 3. Увидеть карту, прогнозы и алерты

Откройте [дашборд](http://localhost:8002) в браузере; рекомендуемый размер окна — 1920×1080.

1. В шапке найдите источник «Официальный эмулятор NDTP → ML», идентификатор `run-…`, ускорение, время данных и состояние «идёт». Время данных должно двигаться, ТС — появляться на карте и в списке.
2. Выберите ТС с прогнозом. Карточка показывает задержку в секундах/минутах, целевую остановку и ожидаемое прибытие. Модель выбирает первую плановую остановку в интервале от 10 до 15 минут после текущего времени данных.
3. В маршруте различаются пройденная часть, путь впереди и целевая остановка. Остановки привязаны к расписанию наряда ТС. Линия приближённо восстановлена по GPS, но не является официальной трассой или результатом map matching; при отсутствии достаточных GPS-данных участок соединяет соседние остановки напрямую.
4. Откройте «Результат модели» в карточке: там видны исходный кадр NDTP, контекст и артефакт модели. Они позволяют связать показанное число с реальным запросом.
5. При предупреждении откройте «События», выберите событие, нажмите «Взять в работу» и добавьте заметку. История действий доступна в интерфейсе; она хранится только в этом браузере и очищается при новом прогоне.

Backend создаёт алерт при актуальном прогнозе задержки **больше 120 секунд**, когда прогноз относится к полному текущему контексту. Для одной пары ТС/цель действует пауза между алертами 300 секунд времени данных. Наличие алерта зависит от реальных прогнозов; мгновенное событие после старта не гарантируется.

«Нет прогноза» с объяснением — допустимый результат: например, в горизонте 10–15 минут нет плановой остановки или ещё не наблюдалась пройденная остановка. Значения «обновляется» и «устарел» нужно читать вместе с возрастом результата. При смене цели интерфейс может временно удерживать предыдущую цель вместе с её прогнозом; это подписано, а не выдаётся за новый результат.

Факт до цели, прогноз модели на цели и допущение «тот же сдвиг» после цели подписаны отдельно. Последнее не является прогнозом модели на каждую остановку.

## 4. Проверить метрики и API

Откройте «Диагностика» на дашборде или запросите JSON:

```bash
curl -fsS http://localhost:8002/api/snapshot
curl -fsS http://localhost:8001/v1/ingest
curl -fsS http://localhost:8002/api/routes
curl -fsS http://localhost:8002/api/build
```

| Где | Что проверять |
|---|---|
| `/api/snapshot` → `snapshot.run` | Прогон, время данных, `accepted_frames`, возраст кадра, состояние драйвера, доли прореживания `thinned_ratio` и повторов `repeat_ratio` |
| `/api/snapshot` → `snapshot.vehicles` | `prediction_s`, целевая остановка, `prediction_state`, возраст прогноза, `status`, `reason`, `alert` |
| `/api/snapshot` → `snapshot.ingest` | Растущий `accepted`; `dropped`, `errors`, `queue_depth` для диагностики входного потока |
| `/api/snapshot` → `snapshot.processing` | `ml_succeeded`, `ml_failed`, `ml_queue_depth`, `ml_dropped_queue_full` и счётчики наблюдений остановок |
| `/v1/ingest` | Подробные счётчики NDTP, активные соединения и журнал исходов кадров |
| `/api/routes` и `/api/route/{tr_id}` | Маршруты обзора и подробный контекст выбранного ТС; вместо `{tr_id}` подставьте ID из snapshot |
| `/api/build` | Commit сборки и SHA-256 раздаваемых файлов интерфейса |

Успех всей цепочки: snapshot имеет `status: online`, кадры принимаются, `ml_succeeded` растёт, у части ТС появляется `prediction_s`, а карточка соответствует выбранной цели. Счётчики отражают работоспособность текущего прогона; они не измеряют MAE и не доказывают предупреждение до начала задержки. Отдельного Prometheus `/metrics` сейчас нет. Измерения производительности и их условия приведены в [локальном runbook](local-demo.md#историческое-t-4t-6-до-единого-демо); исторические числа нельзя приписывать текущему прогону.

Swagger с формами запросов доступен после запуска: [ML](http://localhost:8000/docs), [Backend](http://localhost:8001/docs), [Consumer](http://localhost:8002/docs). Актуальная машинная спецификация каждого работающего сервиса — по его `/openapi.json`.

Сохранённая документация: [ML OpenAPI](../api/openapi.json), [Backend OpenAPI](../api/backend-openapi.json), [Consumer OpenAPI](../api/consumer-openapi.json), [описание Backend v1](../api/backend-v1.md), [PyDoc модулей Python](../pydoc/index.html). HTML PyDoc можно открыть локально после clone. Если установлен Python 3, для удобного просмотра запустите:

```bash
python3 -m http.server 8010 --bind 127.0.0.1 --directory docs
```

Затем откройте [PyDoc](http://localhost:8010/pydoc/). Этот необязательный сервер не входит в Docker-стек; остановка — `Ctrl+C` в его терминале.

## 5. Дополнительно: исторический NDTP replay

Это отдельная проверка протокола и инференса скриптом `scripts/replay_ndtp.py`, без официального эмулятора. В Compose нет отдельного профиля или сервиса `replay`. Основной показ жюри — разделы 1–4.

Не подавайте replay в работающий прогон эмулятора: режимы используют разные часы. Сначала завершите свой демонстрационный стек командой из раздела 7. Затем поднимите три сервиса со временем исходного датасета:

```bash
SOURCE_CLOCK=dataset_wall SOURCE_COMMIT=$(git describe --always --dirty --abbrev=40) docker compose up -d --build --force-recreate ml backend consumer
curl -fsS http://localhost:8001/ready
```

В ответе должны быть `source_clock: dataset_wall` и `clock_mapping` с `dataset_origin: 2026-01-06T00:00:00`, `epoch_origin: 1700000000`, `rate: 1`. Подайте историческое окно из контейнера Backend; локальная установка Python-зависимостей не нужна:

```bash
docker compose exec -T backend python -m scripts.replay_ndtp \
  --traffic /data/validate/traffic.csv \
  --host 127.0.0.1 --port 9201 \
  --backend-url http://127.0.0.1:8001 \
  --start '2026-01-06 03:20:00' --end '2026-01-06 03:45:00' \
  --speedup 30
```

Sender сортирует строки по времени получения, перед каждым NDTP-кадром двигает часы Backend через `POST /v1/replay/clock` и ждёт подтверждение именно своего кадра. Завершение без ошибки печатает JSON с `sent`, `duplicate`, `units`, `elapsed_wall_s`. `duplicate` означает wire-дубликаты и само по себе не является ошибкой.

Прогнозы и счётчики проверяются теми же `/api/snapshot` и `/v1/ingest`. В этом режиме `snapshot.run` равен `null`; дашборд сообщает режим `dataset_wall`, а ускорение относится к sender, не к прогону официального эмулятора. Повторять то же окно в том же Backend нельзя: часы не двигаются назад. Для повторения завершите стек и снова выполните запуск с `--force-recreate`.

## 6. Если результат не появился

| Симптом | Что проверить и сделать |
|---|---|
| `No such image: ndtp-telemetry-emulator:1.0` | Загрузить tar через `docker load`; Compose намеренно не скачивает официальный образ |
| `ml` не healthy | `docker compose logs --tail=50 ml`; наличие трёх файлов модели и правильный `MODEL_DIR` |
| `backend` не healthy | `docker compose logs --tail=50 backend`; два файла `data/validate/` и правильный `DATA_DIR` |
| Долго `waiting_driver`, `failed` или `stalled` | `docker compose --profile demo logs --tail=50 driver emulator backend`; причина отказа также есть в `run.driver.reason` |
| `run_conflict` или `run_already_registered` | В этом Backend уже есть прогон. Новый прогон запускается общей командой recreate из раздела 2 |
| `future simulation event` | Проверить часы контейнеров. В основном сценарии Backend и эмулятор должны работать вместе в Compose |
| Карточка сообщает `no_target_in_horizon` | Дождаться плановой остановки в горизонте 10–15 минут или выбрать другое ТС; это ограничение данных |
| `ml_unreachable_or_timeout` | Проверить `ml` и его логи; интерфейс показывает последний результат с признаком деградации |
| «Карта недоступна» | Проверить `consumer/map/moscow.pmtiles` и пересобрать стек; список и карточки доступны без карты |
| `Sender clock origins differ from Backend /ready clock_mapping` | Replay запущен против неправильного режима; проверить запуск `SOURCE_CLOCK=dataset_wall` из раздела 5 |
| `source_commit: unknown` | При следующем запуске передать `SOURCE_COMMIT`, как в разделе 2 |

Детальные настройки, состояния прогона и ограничения — в [локальном runbook](local-demo.md). Прогноз имеет ограниченную область применимости: обучение на одном дне, точечный результат без вероятностей и без причин задержки. Точность offline-модели и качество приближённого определения пройденных остановок — разные величины.

## 7. Перезапустить или остановить

Для нового прогона официального эмулятора повторите команду раздела 2. Она сбрасывает состояние в памяти и выдаёт новый `run_id`; открытый дашборд очищает историю предыдущего прогона автоматически.

Остановка всех сервисов:

```bash
docker compose --profile demo down
```

Файлы модели, карты и исходных данных остаются на диске. Прогнозы, счётчики и состояние Backend хранились в памяти, поэтому новый запуск начинается с нуля.
