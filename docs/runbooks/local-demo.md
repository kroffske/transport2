# Локальный NDTP demo

Демо одно, другого режима нет. Официальный эмулятор `ndtp-telemetry-emulator:1.0` (образ из `data/emulator/ndtp-telemetry-emulator.tar`, не модифицирован) отправляет NDTP нескольких ТС в Backend. Координаты ему подаёт драйвер `scripts/emulator_driver.py`: он читает GPS окна из `data/validate/traffic.csv` и штатным `POST /api/config` задаёт эмулятору точку каждого ТС. Backend по расписанию строит контекст, вызывает реальную модель в отдельном сервисе `ml`, consumer отдаёт snapshot и маршрутный контекст, а браузер рисует карту с прогнозом задержки ([`dashboard/README.md`](../../dashboard/README.md)).

```text
traffic.csv ─► driver ─POST /api/config─► emulator ─NDTP─► backend ─HTTP─► ml
                 │                                          │
                 └──POST /v1/run, heartbeat─────────────────┘
                                                            └─► consumer :8002 ─► браузер
```

Значений, заданных вручную, на экране нет. Если Backend, ML или данные недоступны, UI показывает причину, а не подставляет числа.

## Что нужно заранее

Файлы ниже не хранятся в Git; собранный интерфейс `consumer/static/` хранится. Пути указаны от корня основного checkout.

| Что | Где | Проверка |
|---|---|---|
| Docker с Compose v2 | — | `docker compose version` |
| Образ официального эмулятора | `data/emulator/ndtp-telemetry-emulator.tar` → `docker load` | `docker image inspect ndtp-telemetry-emulator:1.0` |
| Данные validate | `data/validate/traffic.csv`, `data/validate/schedule_plan.csv` | `ls data/validate` |
| Модель | `models/final/` в репозитории (`final_model.cbm`, `final_model.json`, `vehicle_origins.csv`) | `cd models/final && shasum -a 256 -c SHA256SUMS` |
| Карта | `consumer/map/moscow.pmtiles` (источник и SHA-256 — в `consumer/map/manifest.json`) | `shasum -a 256 consumer/map/moscow.pmtiles` |

Образ эмулятора загружается один раз:

```bash
docker load -i data/emulator/ndtp-telemetry-emulator.tar
```

Compose никогда не скачивает этот образ (`pull_policy: never`). Образ собран под `linux/amd64`; на Apple Silicon он работает через эмуляцию Docker Desktop.

Если данные или модель лежат в другом каталоге (например, запуск из отдельного worktree), передайте абсолютные пути: `DATA_DIR=<checkout>/data MODEL_DIR=<checkout>/.local/validate-tuning-2026-09-26`. Обе переменные монтируются только на чтение.

## Запуск и перезапуск: одна команда

Из корня репозитория:

```bash
SOURCE_COMMIT=$(git describe --always --dirty --abbrev=40) docker compose --profile demo up -d --build --force-recreate --remove-orphans
```

Затем откройте <http://localhost:8002>. Экран рассчитан на 1920×1080.

Эта же команда и перезапускает демо с нуля. `--force-recreate` пересоздаёт все пять сервисов профиля `demo` (`ml`, `backend`, `consumer`, `emulator`, `driver`), `--remove-orphans` убирает контейнеры старых профилей. Состояние Backend и consumer живёт только в памяти процесса, поэтому после recreate:

- Backend получает новый прогон с новым `run_id`, часы данных снова начинаются с начала окна;
- история ТС, прогнозы и счётчики начинаются с нуля;
- страница, уже открытая в браузере, видит новый `run_id` в snapshot и сама очищает события, историю, заметки, выбор и маршрут. Перезагружать её не нужно.

Endpoint сброса без recreate нет. `SOURCE_COMMIT` нужен только для строки сборки в «Диагностике»: без него там честно написано `unknown`. Грязное рабочее дерево видно как `<sha>-dirty`.

Остановка всего стека: `docker compose --profile demo down`.

### Первые минуты

1. `ml`, `backend`, `consumer` становятся `healthy`, emulator стартует. Шапка показывает «ожидание драйвера эмулятора».
2. Драйвер ждёт `/ready` Backend и API эмулятора, регистрирует прогон (`POST /v1/run`), и только после этого настраивает эмулятор. Шапка: «запуск: кадров ещё нет».
3. Первые кадры NDTP приняты — «идёт · N %». ТС появляются на карте; прогнозы модели приходят по мере того, как у ТС находятся наблюдённая остановка и цель.
4. Когда окно данных закончилось, драйвер очищает конфиг эмулятора и сообщает «завершён». Контейнер `driver` завершается с кодом 0; остальные сервисы продолжают работать.

Проверки без вмешательства в стек:

```bash
docker compose --profile demo ps
curl -s http://localhost:8002/api/snapshot | head -c 300
curl -s http://localhost:8002/api/build
docker compose --profile demo logs --no-log-prefix driver | tail -n 3
```

В логе драйвера — JSON-строки `feed_loaded`, `run_registered`, `heartbeat` (с `thinned_ratio`, `repeat_ratio`, счётчиками), в конце `run_completed` или `run_failed`.

## Настройки прогона

Переменные читаются командой запуска из окружения shell. Чтобы применить новое значение, выполните ту же команду запуска с ним, например:

```bash
DEMO_SPEEDUP=10 DEMO_POST_PERIOD_S=1 SOURCE_COMMIT=$(git describe --always --dirty --abbrev=40) docker compose --profile demo up -d --build --force-recreate --remove-orphans
```

Следующий запуск без этих переменных вернёт значения по умолчанию.

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DEMO_SPEEDUP` | `5` | Ускорение: целое, Backend принимает 1–100. 1 минута показа = N минут данных |
| `DEMO_POST_PERIOD_S` | `2` | Период `POST /api/config` драйвера в секундах wall, от 1 до 5. Каждый POST отправляет по одной точке на ТС |
| `DEMO_WINDOW` | `06:30-08:30` | Окно данных дня 2026-01-06. В окне по умолчанию 16 активных ТС. При ×5 показ длится около 24 мин, при ×10 — около 12 мин |
| `DEMO_REPEAT_MAX_S` | `30` | Сколько секунд данных драйвер повторяет последнюю точку ТС, если новой нет. Затем ТС убирается из конфига эмулятора до следующей точки |
| `MODEL_DIR` | `./models/final` | Каталог модели для `ml` |
| `DATA_DIR` | `./data` | Каталог данных для `backend` и `driver` |
| `EMULATOR_IMAGE` | `ndtp-telemetry-emulator:1.0` | Тег загруженного образа эмулятора |

**Компромисс ускорения.** За один POST проходит `DEMO_SPEEDUP × DEMO_POST_PERIOD_S` секунд данных. Если в этом отрезке у ТС было несколько GPS-точек, уходит последняя, а остальные прореживаются. При ×5 и P=2 с отправляется примерно 70 % точек окна. ×10 даёт то же только при P=1 с. Если произведение больше 10 с, драйвер пишет предупреждение в лог. Фактическую долю видно в «Диагностике»: `thinned_ratio` — доля точек окна, не отправленных из-за прореживания; `repeat_ratio` — доля отправок, которые повторили последнюю точку. На живом стеке ×5/P=2 и ×10/P=1 дали `thinned_ratio` около 0,27–0,29.

## Как читать экран

**Шапка:** источник («Официальный эмулятор NDTP → ML»), короткий `run_id` (полный — во всплывающей подсказке и в «Диагностике»), индикатор ускорения, время данных, состояние прогона и прогресс.

**Индикатор ускорения** «Ускорение ×5: 1 мин показа = 5 мин данных» берёт N только из `snapshot.run.speedup`, то есть из Backend. Часы Backend идут именно так: на живом стеке отношение прироста времени данных к приросту реального времени было 4,999 при ×5 и 9,995 при ×10.

**Состояния прогона** (`run.state`, владелец — Backend):

| Состояние | Подпись в шапке | Что это значит |
|---|---|---|
| `waiting_driver` | ожидание драйвера эмулятора | Backend поднят, прогон ещё не зарегистрирован. ТС в snapshot нет, кадры NDTP отклоняются со счётчиком `rejected_no_run` |
| `starting` | запуск: кадров ещё нет | Прогон зарегистрирован, принятых кадров пока нет |
| `running` | идёт | Последний принятый кадр не старше 30 с реального времени |
| `completed` | завершён | Драйвер прошёл всё окно и сообщил об этом. Финальное состояние |
| `failed` | драйвер завершился с ошибкой | Драйвер сообщил об ошибке; причина — в подсказке шапки и в «Диагностике». Финальное |
| `stalled` | остановился: нет кадров дольше 30 с | Backend не получает кадров больше 30 с (в том числе из `starting`). Если кадры пошли снова — обратно `running` |

Прогресс — доля пройденного окна данных.

**Карта и обозначения.** Условные обозначения всегда видны в легенде на экране; точную форму и цвет маркеров смотрите там. Легенда различает ТС по уровню прогноза задержки у цели (до 2 мин включительно, больше 2 мин, от 5 мин) и отдельно ТС без прогноза, а для выбранного ТС — путь по GPS прогона, пройденную часть, остановку, пройденную остановку и цель. Уровень ТС — это величина прогноза у цели, а не вероятность.

**Выбранное ТС.** Клик по ТС на карте или в списке показывает его маршрутный контекст (`/api/route/{tr_id}`):

- **серая линия «путь по GPS прогона»** — траектория этого ТС в текущем окне данных, построенная из тех же GPS-точек, что подаёт драйвер. Это не официальная трасса маршрута и не вход модели: `route_id` и трасс в данных нет;
- **пройденная часть** — только достоверные GPS-точки, которые Backend действительно принял в этом прогоне;
- **остановки** — плановые прибытия этого ТС из расписания в окне от «сейчас − 5 мин» до «цель + 15 мин» (без цели — до «сейчас + 30 мин»), не больше 40. Пройденные отмечены отдельно. Остановка без координаты или вне карты на карте не рисуется; в карточке она остаётся с пометкой, а её число показано;
- **цель** — первая плановая остановка ТС через 10–15 мин от текущего времени данных. Именно для неё модель даёт прогноз. Подписи времени есть у цели и у ближайшей будущей остановки, у остальных — при наведении и в карточке.

**Карточка ТС:**

| Строка | Откуда значение |
|---|---|
| «Текущее опоздание» (факт) | `cur_dev_s`: Backend оценивает его по прошлым GPS и плану |
| Остановки до цели | план + текущее опоздание, подпись «по факту, не прогноз» |
| Цель | план + `prediction_s` модели, подпись «прогноз модели». Рядом — кадр NDTP, номер контекста, версия модели и хэш артефакта, на которых посчитан результат |
| Остановки после цели | план + тот же `prediction_s`, подпись «допущение: тот же сдвиг». Модель для них прогноз не давала. Переключатель «Показывать сдвиг после цели» (по умолчанию включён) скрывает это допущение |

Если прогноза нет, карточка пишет причину по-русски, и статус ТС не зелёный. Например: «у ТС нет плановой остановки через 10–15 мин», «не определена пройденная остановка — нет факта опоздания», «модель недоступна (нет ответа или timeout)», «последняя позиция GPS недостоверна». Неизвестный код причины показывается как есть. В окне по умолчанию одновременно без прогноза обычно около половины ТС: у многих в ближайшие 10–15 мин нет плановой остановки. Это свойство данных, а не сбой.

**События и действия диспетчера** работают на живых данных: событие открывается по реальному предупреждению (прогноз > 2 мин), дальше «События» → карточка → «Взять в работу» → заметка → история. Всё это хранится только в этом браузере и очищается при новом `run_id`. Подробно — в [`dashboard/README.md`](../../dashboard/README.md).

**«Диагностика»** показывает все поля прогона (`run_id`, ускорение и период POST, `thinned_ratio`, `repeat_ratio`, принятые кадры, возраст последнего кадра, состояние драйвера), счётчики ingest и ML, а также сборку: `source_commit`, `dashboard_bundle_sha256`, `consumer_static_sha256` и хэши отдельных файлов из `/api/build`.

## Показ за 2–3 минуты

Запустите стек заранее, чтобы прогон был в состоянии «идёт» и у части ТС уже были прогнозы.

1. Шапка: «Это поток официального эмулятора NDTP, которого кормят GPS из данных. Ускорение ×5: одна минута показа — пять минут данных».
2. Обзор карты и списка: ТС с прогнозом и без него; у ТС без прогноза в карточке написана причина.
3. Выбрать ТС с прогнозом: путь по GPS прогона, пройденная часть, остановки, цель через 10–15 мин. Карточка: факт до цели, прогноз модели на цели, допущение после цели.
4. «Результат модели» в карточке: кадр NDTP, контекст и артефакт модели. Новый результат модели меняет их в той же карточке.
5. Если есть предупреждение: «События» → карточка → «Взять в работу» → заметка → история.

Не говорить: «доказанное предупреждение за 10–15 минут» (lead-time не измерялся), «официальная трасса маршрута» (это GPS-путь), «прогноз на каждой остановке» (модель даёт прогноз только на цели), «официальный score N» (ответа платформы нет), «команда отправлена водителю» (связь с водителем — прототип текста).

## Ограничения

- **Время NDTP ставит эмулятор, а не данные.** Каждый пакет получает текущее время отправки; Backend переводит его во время данных через зарегистрированное ускорение. Поэтому реальные задержки доставки и неупорядоченность исходных данных не воспроизводятся. Драйвер упорядочивает точки каждого ТС по `event_time`, пропускает строки `is_hist_data=True` и немонотонные строки и считает их (`skipped_hist`, `skipped_nonmonotonic`).
- **Маршрутов нет в данных.** В `traffic.csv` и `schedule_plan.csv` нет `route_id`, трасс и устойчивого ID физической остановки. Серая линия — только GPS-траектория прогона.
- **Горизонт модели — 10–15 мин, а не следующая остановка.** Модель прогнозирует задержку на первой плановой остановке в интервале (T+10 мин, T+15 мин]. Между текущим положением и целью обычно несколько остановок; значения для них — факт или допущение, как подписано в карточке.
- **Причина и вероятность задержки не показываются.** Модель точечная; причины не угадываются.
- **Модель обучена на одном дне** (2026-01-06). Окно можно сдвигать только внутри этого дня.
- Прореживание при ускорении описано в разделе «Настройки прогона».
- Локальная MAE модели 44,01 с на validate — это не официальный score и не точность в этом потоке. Раннее предупреждение (lead-time до начала задержки) не измерялось.

## Troubleshooting

| Симптом | Причина и что делать |
|---|---|
| `No such image: ndtp-telemetry-emulator:1.0` при запуске | Образ не загружен, а pull запрещён (`pull_policy: never`). Выполните `docker load -i data/emulator/ndtp-telemetry-emulator.tar` и повторите команду запуска |
| `ml` не становится healthy | Нет файлов модели в `MODEL_DIR` или неверный путь. Проверьте `ls .local/validate-tuning-2026-09-26/final_model.cbm` или задайте абсолютный `MODEL_DIR` |
| `backend` не становится healthy | Нет `data/validate/traffic.csv` или `schedule_plan.csv` в `DATA_DIR` |
| Шапка долго «ожидание драйвера эмулятора» | Драйвер не зарегистрировал прогон. Смотрите `docker compose --profile demo logs driver`: `config_error` — неверные `DEMO_*`; `driver_failed` с `not ready within` — Backend или эмулятор не ответили за 180 с |
| Ручной `docker compose --profile demo run --rm driver` пишет `run_conflict`, exit 3 | Прогон в этом Backend уже зарегистрирован (`409 run_already_registered`). Второй драйвер не трогает конфиг эмулятора, первый продолжает работу. Новый прогон — только командой запуска с recreate |
| «остановился: нет кадров дольше 30 с» (`stalled`) | Backend не получает NDTP. Проверьте, что `driver` и `emulator` работают (`docker compose --profile demo ps`), и посмотрите лог драйвера. Если драйвер упал, состояние будет `failed` с причиной. Восстановление — командой запуска |
| Кадры не принимаются, в `curl -s http://localhost:8001/v1/ingest` растёт `errors_state`, в `outcomes` — `future simulation event` | Время пакета от эмулятора оказалось позже времени приёма Backend: расходятся часы эмулятора и Backend. Так бывает, если Backend запущен на host, а эмулятор в VM Docker. В compose оба работают в одной VM; запускайте демо только командой выше |
| У ТС «Прогноза нет: у ТС нет плановой остановки через 10–15 мин» | Нормально: в горизонте модели у ТС нет плановой остановки. Прогноз появится, когда такая остановка войдёт в горизонт |
| «модель недоступна (нет ответа или timeout)» (`ml_unreachable_or_timeout`) | Сервис `ml` остановлен или не отвечает за 3 с. Проверьте `docker compose --profile demo ps ml`. После старта `ml` прогнозы возвращаются примерно через 10 с |
| «Карта недоступна» | Нет `consumer/map/moscow.pmtiles` в образе consumer. Положите файл и повторите команду запуска. Список и карточка работают и без карты |
| В «Диагностике» `source_commit: unknown` | Команда запущена без `SOURCE_COMMIT=…` |
| Ошибка EOF при загрузке `python:3.12-slim` | Docker Hub недоступен. Рабочий fallback: `docker pull mirror.gcr.io/library/python:3.12-slim && docker tag mirror.gcr.io/library/python:3.12-slim python:3.12-slim` |
| `curl http://127.0.0.1:8000/ready` отвечает не ML-сервис | На host порт `127.0.0.1:8000` занят другим процессом. Контейнер `ml` отвечает на `http://[::1]:8000` |

## Проверки

```bash
.venv/bin/python -m pytest tests -q
npm ci --prefix dashboard
npm --prefix dashboard test
npm --prefix dashboard run build
UI_URL=http://localhost:8002 npm --prefix dashboard run check:browser
```

- `pytest` покрывает Backend (прогон, lifecycle, route, свежесть прогноза), драйвер (fake HTTP эмулятора и Backend), consumer (`/api/route`, `/api/build`).
- `npm run build` пересобирает `consumer/static/`; bundles вручную не правятся. После сборки выполните команду запуска, чтобы consumer раздал новую сборку.
- `check:browser` работает на 1920×1080 через Playwright Chromium против запущенного стека. Проходы `live` идут без подмены запросов, ожидаемые значения читаются из того же API. Проходы `regression` явно подписаны: они подменяют `/api/snapshot` и `/api/route` фиксированными ответами, чтобы проверить состояния, которые нельзя вызвать по требованию. Это не evidence живой цепочки. `UI_EVIDENCE_DIR=<абсолютный каталог>` сохраняет скриншоты; `UI_LIVE_EVENT_WAIT_S=90` ждёт реального предупреждения для прохода M1.
