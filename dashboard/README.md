# Диспетчерская карта задержек Москвы

Экран единого демо: 2D-карта города сверху, транспорт текущего прогона официального эмулятора NDTP, маршрутный контекст выбранного ТС с прогнозом модели и карточка. Рассчитан на Full HD 1920×1080. Запуск стека, настройки прогона и troubleshooting — в [local demo](../docs/runbooks/local-demo.md).

Источник данных один: consumer `/api/snapshot` → Backend `/v1/vehicles`, для выбранного ТС — consumer `/api/route/{tr_id}` → Backend `/v1/route/{tr_id}` ([контракт](../docs/api/backend-v1.md)). Сценарных значений, режимов и `?mode=` больше нет. Браузер опрашивает consumer раз в 1,5 с и не вычисляет ни маршруты, ни прогнозы.

## Что на экране

- **Шапка прогона** (из `snapshot.run`): источник «Официальный эмулятор NDTP → ML», короткий `run_id` (полный — в подсказке и «Диагностике»), «Ускорение ×N: 1 мин показа = N мин данных» (N только из `run.speedup`), время данных, состояние прогона с прогрессом. Если `snapshot.run` равен `null` (Backend запущен не в `SOURCE_CLOCK=simulation`), шапка пишет «Backend без прогона · часы <source_clock>» и ускорение не выдумывает. Состояния прогона и их смысл — в [runbook](../docs/runbooks/local-demo.md#как-читать-экран).
- **Верхняя панель:** состояние Backend, кнопка «События» со счётчиком непрочитанных, раскрываемая «Диагностика».
- **Карта** занимает всё, кроме правой панели. Вид всегда сверху; pan, zoom и «Обзор» работают. Строка «Требует внимания» слева сверху ведёт к самому срочному ТС.
- **Легенда** на карте — единственное описание обозначений: ТС по уровню прогноза у цели (≤ 2 мин, > 2 мин, ≥ 5 мин) и без прогноза; для выбранного ТС — путь по GPS прогона, пройденная часть, остановка, пройденная остановка, цель. Уровень — величина прогноза, не вероятность. Точную форму и цвет маркеров смотрите в легенде: они описаны там, а не здесь. ТС без достоверной позиции остаётся в списке, даже если его нельзя нарисовать на карте.
- **Правая панель:** фильтры «Все / С предупреждениями / Нет прогноза» со счётчиками текущего снимка, поиск по ID, «Сбросить выбор», список по срочности и карточка выбранного ТС.

### Маршрутный контекст выбранного ТС

Маршрут запрашивается при выборе ТС, затем не чаще раза в 3 с и сразу, если в snapshot сменились цель или прогноз.

| Слой | Что это | Чем не является |
|---|---|---|
| Путь по GPS прогона | Траектория ТС в текущем окне данных из тех же GPS-точек, что подаёт драйвер эмулятора | Не официальная трасса маршрута и не вход модели: `route_id` и трасс в данных нет |
| Пройдено | Достоверные GPS-точки, которые Backend принял в этом прогоне | — |
| Остановки | Плановые прибытия ТС в окне «сейчас − 5 мин … цель + 15 мин», не больше 40; пройденные отмечены отдельно | Не устойчивые ID физических остановок |
| Цель | Первая плановая остановка через 10–15 мин от времени данных — на неё прогнозирует модель | Не «следующая остановка» |

Подписи времени — только у цели и ближайшей будущей остановки, остальные — по наведению и в карточке. Точка без координаты, в `(0,0)` или вне карты не рисуется и линию через неё не соединяет. В карточке такая остановка остаётся с пометкой «Координаты нет — на карте не показана», а счётчики `stops_dropped` и `stops_truncated` показаны. Ответ `/api/route` 404 даёт «Маршрутного контекста нет: …». Если consumer вернул offline, а ответ по этому ТС уже был, показан последний полученный контекст с пометкой, что он не обновляется.

### Карточка ТС

- **«Текущее опоздание» (факт)** — `cur_dev_s`, оценка Backend по прошлым GPS и плану.
- **Цель прогноза** — план + `prediction_s` модели, подпись «прогноз модели». Поле «Результат модели» показывает принятый кадр NDTP (`prediction_input_frame_id`), номер контекста, версию модели и хэш артефакта. Бейдж «обновляется» с возрастом означает, что новый кадр той же цели уже пришёл, а свежий прогноз ещё считается.
- **Остановки по плану:** до цели — план + текущее опоздание, «по факту, не прогноз»; цель — прогноз модели; после цели — план + тот же `prediction_s`, «допущение: тот же сдвиг». Переключатель «Показывать сдвиг после цели» (по умолчанию включён) скрывает допущение.
- **Нет прогноза:** «Прогноза нет: <причина>» по-русски (`reasons.js`), например «у ТС нет плановой остановки через 10–15 мин» или «модель недоступна (нет ответа или timeout)». Неизвестный код показывается как есть.
- «Ревизия строки ТС»: `revision` snapshot и `vehicle_revision` маршрута. Предупреждение о расхождении появляется, только если ревизии равны, а значения разные.

### События и действия диспетчера

Событие — эпизод предупреждения (прогноз > 2 мин) одного ТС. Состояния: «Активно»; «Мониторинг потерян» — у ТС нет актуальных данных непрерывно не меньше `LOST_AFTER_S = 15` с реального времени, событие **не** закрыто; «Задержка закончилась» — прогноз снова ≤ 2 мин. Более короткий пробел (например, пока считается прогноз для новой цели) состояние не меняет, историю не пишет и непрочитанным не отмечает. Новое предупреждение после завершения открывает новый эпизод.

- **Центр событий** («События»): активные и завершённые события, значения, пик, время открытия, статус обработки, непрочитанные. Клик выбирает ТС и центрирует карту.
- **Toast** — один на новый эпизод.
- **Прочитано**, **«Взять в работу» / «Вернуть в новые»** и **«Задержка закончилась»** — разные состояния.
- **Заметка** — простой текст до 280 символов; HTML не исполняется. История события показывает время по часам данных.
- **Связь с водителем · прототип** готовит текст для водителя и ничего не отправляет. «Скопировать текст» сообщает об успехе только после записи в буфер обмена.
- Всё это хранится **только в этом браузере** и очищается при смене `run_id` в snapshot (recreate стека), вместе с выбором, фильтрами и маршрутом. Первый снимок страницы сбросом не считается.

Ошибка Backend показывается честно: «Backend недоступен · последний снимок …» с устаревшими значениями (предупреждения по ним не оцениваются) либо «данных нет», если успешного снимка не было. Если нет локального архива плиток, `manifest.json` или WebGL — «Карта недоступна: …»; список и карточка продолжают работать.

«Диагностика»: все поля `run` (включая `thinned_ratio`, `repeat_ratio`, период POST драйвера, принятые кадры, состояние и причину драйвера), revision, часы, ingest- и ML-счётчики, происхождение геоосновы и сборка из consumer `/api/build`: `source_commit`, `dashboard_bundle_sha256`, `consumer_static_sha256` и SHA-256 отдельных файлов. По ним видно, какую сборку получил браузер.

## Устройство

- `app.js` — точка сборки: MapLibre GL JS с локальными PMTiles, слои маршрутного контекста, custom-слой Three.js для маркеров ТС и цели (общая камера и WebGL context MapLibre), DOM-подписи, панели, карточка, центр событий, toast, «Диагностика» и опрос consumer.
- `run.js` — тексты шапки прогона (источник, `run_id`, ускорение, время данных, состояние, прогресс) и определение смены прогона по `run_id`.
- `route-context.js` — показ ролей остановок (факт / прогноз модели / допущение), проверка координат (`MAP_BOUNDS`, `(0,0)`, `null`), разрыв линии на плохой точке, выбор подписываемых остановок.
- `reasons.js` — русские подписи кодов причин Backend и ML.
- `incidents.js` — классификация строки (предупреждение > 120 с, сильная задержка ≥ 300 с, нет данных), фильтры, сортировка, поиск и локальное хранилище событий.
- `map-labels.js` — раскладка подписей без пересечений с приоритетом «выбранное ТС → цель → ближайшая остановка → остальные».
- `dom.js` — патчинг DOM между опросами, чтобы клик, фокус и прокрутка переживали обновление.

## Сборка и проверки

```bash
npm ci --prefix dashboard
npm --prefix dashboard test
npm --prefix dashboard run build
UI_URL=http://localhost:8002 npm --prefix dashboard run check:browser
```

- `test` — unit-тесты `incidents`, `map-labels`, `reasons`, `route-context`, `run`: пробел < `LOST_AFTER_S` не переводит событие в «Мониторинг потерян», сброс по `run_id`, форматирование ускорения, классификация остановок до/на/после цели, отбраковка координат, подписи причин, приоритет подписей.
- `build` собирает `consumer/static/{app.js,app.css,map-worker.js}`. Bundles вручную не правятся. Чтобы consumer раздал новую сборку, выполните команду запуска из [runbook](../docs/runbooks/local-demo.md#запуск-и-перезапуск-одна-команда).
- `check:browser` (Playwright Chromium, 1920×1080) — против запущенного стека на `UI_URL`. Проходы `live` не подменяют запросы и берут ожидаемые значения из того же API. Проходы `regression` явно подписаны и подменяют только `/api/snapshot` и `/api/route` (и `/map/moscow.pmtiles` для проверки недоступной карты), чтобы получить состояния, которые нельзя вызвать по требованию: `waiting_driver`, смена `run_id`, Backend offline, плохие координаты, коды причин, M1 на фиксированных данных. Regression-проходы не являются evidence живой цепочки. `UI_EVIDENCE_DIR=<абсолютный каталог>` сохраняет скриншоты, `UI_LIVE_EVENT_WAIT_S=90` ждёт реального предупреждения для M1 на live. Внешние запросы, page errors и console errors считаются провалом.

## Происхождение геоосновы

Локальный PMTiles v3, MVT (слои `earth`, `water`, `landuse`, `roads`, `buildings`, `boundaries` и другие), bbox 37.25,55.50,38.00,56.00, zoom 0–13. Из Protomaps basemap `https://build.protomaps.com/20260925.pmtiles`, OSM replication time **2026-09-25T04:00:00Z**, источник OSM/ODbL (© OpenStreetMap contributors); metadata и sha256 находятся в `consumer/map/manifest.json` и видны в «Диагностике». Это **геометрия OSM**, а не маршрут автобуса. Подписей улиц нет: шрифтовые glyphs не поставляются. Воспроизводимая команда с go-pmtiles v1.31.2:

```sh
pmtiles extract https://build.protomaps.com/20260925.pmtiles consumer/map/moscow.pmtiles --bbox=37.25,55.50,38.00,56.00 --minzoom=0 --maxzoom=13
shasum -a 256 consumer/map/moscow.pmtiles
```

Все JS, CSS, worker и плитки раздаёт consumer по localhost; внешних запросов нет. `/map/moscow.pmtiles` поддерживает HTTP Range.
