# Диспетчерский BI-терминал Москвы

Экран единого демо: 2D-карта города сверху, транспорт текущего прогона официального эмулятора NDTP, маршрутный контекст выбранного ТС с прогнозом модели и карточка. Рассчитан на Full HD 1920×1080. Запуск стека, настройки прогона и troubleshooting — в [local demo](../docs/runbooks/local-demo.md).

Источник данных один: consumer `/api/snapshot` → Backend `/v1/vehicles`, маршруты обзора — consumer `/api/routes` → Backend `/v1/routes` (раз в 10 с), для выбранного ТС — consumer `/api/route/{tr_id}` → Backend `/v1/route/{tr_id}` ([контракт](../docs/api/backend-v1.md)). Сценарных значений, режимов и `?mode=` больше нет. Браузер опрашивает consumer раз в 1,5 с и не вычисляет ни маршруты, ни прогнозы.

## Что на экране

- **Шапка прогона** (из `snapshot.run`): источник «Официальный эмулятор NDTP → ML», короткий `run_id` (полный — в подсказке и «Диагностике»), «×N · 1 мин на экране = N мин данных» (N только из `run.speedup`; уже 1800 px — только «×N», полный текст в подсказке), крупные часы времени данных «06:58» с подписью «время данных» (после завершения — «Данные на 06:58:38 · прогон завершён»), состояние прогона с прогрессом. Если `snapshot.run` равен `null` (Backend запущен не в `SOURCE_CLOCK=simulation`), шапка пишет «Backend без прогона · часы <source_clock>» и ускорение не выдумывает. Состояния прогона и их смысл — в [runbook](../docs/runbooks/local-demo.md#как-читать-экран).
- **Верхняя панель:** состояние Backend, кнопка «Непрочитано N» (открывает очередь), «Маршруты» (набор маршрутов оператора), раскрываемая «Диагностика».
- **«Маршруты» — мои маршруты оператора.** Галочка на маршрут плана (`catalog` из `/api/routes`): подпись — улицы конечных, `route_key`, ТС прогона на нём; отдельный пункт «Без наряда» для ТС без плана; «Все» / «Снять все». По умолчанию — все. Карта, обзорные линии, список «Транспорт», очередь «События», строка «Требует внимания», toast и J/K показывают только ТС выбранных маршрутов; очередь при этом наблюдает все ТС, поэтому скрытый маршрут не переводит события в «Мониторинг потерян», а при возврате маршрута его события на месте. Смена набора снимает групповой выбор событий. Настройки хранятся в `localStorage` браузера (`dispatcher-settings`) в формате, в котором их можно выдавать оператору:

  ```json
  {"format": "transport.dispatcher-settings.v1", "operator": "Диспетчер", "routes": ["R-69ee05", "R-0b1f94"]}
  ```

  `"routes": "all"` — все маршруты, включая появившиеся позже; `"none"` в списке — «Без наряда». Как выводится маршрут (в данных номера маршрута нет) — в [контракте](../docs/api/backend-v1.md). В демо-плане у каждого наряда свой маршрут, т. е. сейчас маршрут и ТС совпадают 1:1.
- **Компоновка.** От 1600 px — три колонки: карта | карточка 440 px | очередь 360 px; пока карточка не открыта, её колонка показывает «Сводку смены». 1100–1599 px — карта | очередь 330 px (320 px уже 1400), карточка — панель 420 px поверх правого края карты; карта при открытии и закрытии панели размер не меняет. Карточка и очередь прокручиваются независимо.
- **Карта** — вид всегда сверху; pan, zoom и «Все ТС» работают. Кадр выбранного ТС: ТС, цель и следующая остановка с отступами от полосы внимания сверху, легенды слева и панели карточки справа; ТС дальше 2 км от маршрута — стрелка у края «ТС id · ~N км →». **Полоса внимания** — только состояние системы: «Backend недоступен», «Прогон завершён», прогон с ошибкой или остановился; в остальное время скрыта. О новых событиях сообщают уведомления внизу справа, список — в очереди.
- **Esc и ×:** Esc закрывает меню, затем карточку (выбор, кольцо на карте и строка очереди остаются; клик по строке вернёт карточку), второй Esc снимает выбор. × — как первый Esc.
- **Горячие клавиши** — в подсказке «?» над очередью (клавиша `?`): J / K — следующее / предыдущее событие, W — взять в работу, S — отложить 5 мин данных, C — закрыть, `/` — поиск ТС, Esc. Подсказки клавиш остаются и на кнопках.
- **Легенда** — вертикальная панель у левого края карты, внизу, по обозначению в строке (выше полосы внимания не растёт, лишнее прокручивается; уже 900 px — компактнее); единственное описание обозначений: ТС по уровню прогноза у цели (≤ 2 мин, 2–5 мин «!», ≥ 5 мин «!!»), без прогноза, нет GPS, «GPS неисправен» (фиолетовый); для маршрута — пройдено, впереди → (до цели), после цели (пунктир), вне маршрута; остановки по роли формой, не цветом: ○ пройдена, ◉ до цели, ◆ цель прогноза, ◌ после цели (допущение). Стрелка у значка ТС — направление движения (`heading`), без `heading` стрелки нет. Уровень — величина прогноза, не вероятность. Точную форму и цвет маркеров смотрите в легенде: они описаны там, а не здесь. ТС без достоверной позиции остаётся в списке, даже если его нельзя нарисовать на карте.
- **Правая колонка:** поле «Поиск ТС по номеру (/)», вкладки «События» и «Транспорт». Очередь распределена по этапам реакции, фильтр-чипы «Все · Новые · В работе · Отложены»; открытое событие держит свою строку (бейдж показывает новое состояние) до снятия выбора или J/K. Уведомления — только о новом событии, возврате из отсрочки и потере мониторинга, одна кнопка «Открыть»; не показываются, если строка события видна в очереди. Выбор открывает карточку ТС и маршрут.

### Маршрутный контекст выбранного ТС

Маршрут запрашивается при выборе ТС, затем не чаще раза в 3 с и сразу, если в snapshot сменились цель или прогноз.

| Слой | Что это | Чем не является |
|---|---|---|
| Маршруты на обзоре | Тонкие приглушённые линии всех ТС прогона: сохранённая форма, приближённо восстановленная по GPS и закреплённая на плановых остановках (`/api/routes`, `line`) | Не официальная трасса и не map matching; перегоны без достаточных данных остаются прямыми |
| Маршрут выбранного ТС | `route_line` из `/api/route`: при `split_reason=on_route` пройденное тускло, впереди ярко со стрелками; деление решает Backend, UI его не вычисляет | Не map matching; GPS-трек (`path`, `passed`) не рисуется |
| Вне маршрута | `off_route=true`: вся линия тускло, пунктирная выноска от ТС к `nearest` с подписью «вне маршрута ~N км» (`route_offset_m`) | Не ошибка прогноза: пространственная сверка с линией наряда за день |
| Остановки | Плановые прибытия ТС в окне «сейчас − 5 мин … цель + 15 мин», не больше 40; пройденные отмечены отдельно | Не устойчивые ID физических остановок |
| Цель | Первая плановая остановка через 10–15 мин от времени данных — на неё прогнозирует модель | Не «следующая остановка» |

Подписи времени — только у цели и ближайшей будущей остановки, остальные — по наведению и в карточке. Точка без координаты, в `(0,0)` или вне карты не рисуется и линию через неё не соединяет. В карточке такая остановка остаётся с пометкой «Координаты нет — на карте не показана», а счётчики `stops_dropped` и `stops_truncated` показаны. Ответ `/api/route` 404 даёт «Маршрутного контекста нет: …». Если consumer вернул offline, а ответ по этому ТС уже был, показан последний полученный контекст с пометкой, что он не обновляется.

### Карточка ТС

- **Порядок:** липкий верх (АВТОБУС id · уровень · ×, блок прогноза, статус события, действия) → предупреждения (вне маршрута, GPS) → остановки → свёрнутые «Шаги реакции» (раскрываются при «Взять в работу»), «История события», «Технические подробности». Основная (тёмная) кнопка — следующее логичное действие: Новое → «Взять в работу», В работе → «Закрыть ▾», Завершено → «Закрыть».
- **Блок прогноза** (`forecast.js`, одно состояние на строку): «Цель прогноза · ост. N (ⓘ)», «По расписанию 08:42», «Ожидается 08:45 · прогноз модели», крупно «Опоздание по прогнозу +3 мин», факт «Сейчас: опаздывает на 1 мин (факт, ост. 4)» и возраст прогноза (время данных; в подсказке — «≈N с на экране при ×5»). Состояния: обновляется (та же цель или удержание Backend без смены цели — значение прежнее); смена цели (`prediction_hold_reason=target_changed`: прошлый результат отдельно, «К новой цели не относится»); «По графику · прогноз готовится» (`warming`, зелёный); «Прогноз устарел»; «Прогноза для цели пока нет» с причиной; «Цель прогноза не выбрана»; цель после конца данных прогона; «ТС пропало» (`lost`, > 5 мин без данных); «Прогон завершён»; «Прогноз не обновляется» (Backend недоступен). В тихих состояниях цифры серые.
- **Формат задержки** один на карточку, очередь и метки: компактно `+3:20`, крупно «+3 мин 20 с», от 10 мин — «+12 мин»; |d| < 30 с — «по графику»; время — ЧЧ:ММ.
- **Остановки:** группы с липкими заголовками — «Пройдено · только расписание» (свёрнуто), «До цели · перенесено текущее опоздание (факт, не прогноз)», «Цель · прогноз модели» (строка инвертирована), «После цели · допущение» (2 строки + «Ещё N», время с «≈», постоянная оговорка «Не прогноз модели. Показан тот же сдвиг, что у цели.»). Значки ✓ ◉ ◆ ◌ подписаны для экранного диктора. Переключатель «Показывать сдвиг после цели» (по умолчанию включён) скрывает допущение. «Результат модели» (кадр NDTP, контекст, версия, хэш) — в «Технических подробностях».
- **Нет прогноза:** «Прогноза нет: <причина>» по-русски (`reasons.js`), например «у ТС нет плановой остановки через 10–15 мин» или «модель недоступна (нет ответа или timeout)». Неизвестный код показывается как есть.
- «Ревизия строки ТС»: `revision` snapshot и `vehicle_revision` маршрута. Предупреждение о расхождении появляется, только если ревизии равны, а значения разные.

### События и действия диспетчера

Событие — эпизод предупреждения (прогноз > 2 мин) одного ТС. Состояния: «Активно»; «Мониторинг потерян» — у ТС нет актуальных данных непрерывно не меньше `LOST_AFTER_S = 15` с реального времени, событие **не** закрыто; «Задержка закончилась» — прогноз снова ≤ 2 мин. Более короткий пробел (например, пока считается прогноз для новой цели) состояние не меняет, историю не пишет и непрочитанным не отмечает. Новое предупреждение после завершения открывает новый эпизод.

- **Очередь:** группы «Требуют реакции», «В работе», «Отложены», «Завершены», счётчики и непрочитанные завершения. Событие хранит время открытия, текущую задержку и пик; выбор центрирует карту на ТС.
- **Таймер реакции:** для нового события задано 90 секунд; события упорядочены по оставшемуся времени реакции, просроченные первыми; при одинаковом сроке выше события с большей задержкой. Это настройка интерфейса, а не измеренный норматив работы диспетчера.
- **Обработка:** «Взять в работу», вернуть в новые, отложить на 2/5/10/15 минут времени данных и снять отсрочку. По истечении отсрочки событие возвращается в очередь с напоминанием.
- **Закрытие с причиной:** водитель уведомлён, ошибка GPS/прогноза, сход/замена ТС, пробка или другое. Закрытие обработки и прекращение задержки — отдельные состояния.
- **Чек-лист:** проверка GPS, связь с водителем, проверка интервала с соседними ТС; при пике задержки от пяти минут — сообщение старшему смены. Отметка фиксирует действие диспетчера, а не выполняет его автоматически.
- **Групповые действия:** выбранные события можно взять в работу, отложить или закрыть; клавиши J/K/W/S/C управляют перемещением и основными действиями.
- **Заметки и история:** текст до 280 символов, изменения состояния и действия с временем по часам данных. HTML в заметках не исполняется.
- **Связь с водителем:** подготовка и копирование текста; отправка остаётся за диспетчером по штатному каналу.
- **Неисправный GPS:** ручная отметка исключает ТС из текущих предупреждений и закрывает событие с соответствующей причиной.
- **Хранение:** очередь, история и заметки хранятся в sessionStorage под ключом `t7-queue:<run_id>`: перезагрузка страницы их восстанавливает, смена `run_id` начинает с пустой очереди.


Ошибка Backend показывается честно: «Backend недоступен · последний снимок …» с устаревшими значениями (предупреждения по ним не оцениваются) либо «данных нет», если успешного снимка не было. Если нет локального архива плиток, `manifest.json` или WebGL — «Карта недоступна: …»; список и карточка продолжают работать.

«Диагностика»: все поля `run` (включая `thinned_ratio`, `repeat_ratio`, период POST драйвера, принятые кадры, состояние и причину драйвера), revision, часы, ingest- и ML-счётчики, происхождение геоосновы и сборка из consumer `/api/build`: `source_commit`, `dashboard_bundle_sha256`, `consumer_static_sha256` и SHA-256 отдельных файлов. По ним видно, какую сборку получил браузер.

## Устройство

- `app.js` — точка сборки: MapLibre GL JS с локальными PMTiles (камера ограничена `CAMERA_BOUNDS` — шире данных, чтобы карта на экране 1920×1080 могла показать все ТС прогона сразу), опрос consumer (`/api/snapshot`, `/api/route`, `/api/routes`), DOM-подписи, панели, карточка, центр событий, toast и «Диагностика».
- `run.js` — тексты шапки прогона (источник, `run_id`, ускорение, время данных, состояние, прогресс) и определение смены прогона по `run_id`.
- `route-context.js` — показ ролей остановок (факт / прогноз модели / допущение), проверка координат (`DATA_BOUNDS` — экстент плиток и `MAP_BBOX` Backend; `(0,0)`, `null`), разрыв линии на плохой точке, выбор подписываемых остановок, прореживание остановок на мелком масштабе, выбор слоёв маршрута по `route_line`, текст расстояния «~N км».
- `route-layers.js` — слои MapLibre маршрутов под транспортным слоем: маршруты обзора, маршрут выбранного ТС (пройдено / впереди со стрелками / тускло), выноска «вне маршрута», остановки с подсказкой по наведению.
- `transport-layer.js` — единственный рендерер значков ТС и цели: custom-слой Three.js в MapLibre (общая камера и WebGL context), bitmap кэшируются по виду значка.
- `map-symbols.js` — вид значков: ТС — скруглённый квадрат с иконкой Lucide `bus`, состояния различаются формой (бейджи, пунктир, кольцо; полный список — в комментарии модуля), отдельная стрелка направления; цель — ромб с Lucide `flag`; рисование на canvas.
- `icons/lucide.js` — геометрия иконок Lucide `bus` и `flag` (см. «Лицензии»).
- `reasons.js` — русские подписи кодов причин Backend и ML.
- `route-scope.js` — настройки оператора `transport.dispatcher-settings.v1`: разбор, список выбора маршрутов, фильтр строки по `route_key`, «все / N из M».
- `event-queue.js` — группы и приоритеты очереди, таймер реакции, отсрочка, причины закрытия, чек-лист и групповые действия.
- `incidents.js` — классификация строки (предупреждение > 120 с, сильная задержка ≥ 300 с, нет данных), фильтры, сортировка, поиск и локальное хранилище событий.
- `map-labels.js` — раскладка подписей без пересечений с приоритетом «выбранное ТС → цель → ближайшая остановка → остальные».
- `dom.js` — патчинг DOM между опросами, чтобы клик, фокус и прокрутка переживали обновление.

## Сборка и проверки

```bash
npm ci --prefix dashboard
npm --prefix dashboard test
npm --prefix dashboard run build
UI_URL=http://localhost:8002 npm --prefix dashboard run check:browser
```

- `test` — unit-тесты `event-queue`, `incidents`, `map-labels`, `map-symbols`, `reasons`, `route-context`, `route-scope`, `run`: пробел < `LOST_AFTER_S` не переводит событие в «Мониторинг потерян», сброс по `run_id`, форматирование ускорения, классификация остановок до/на/после цели, отбраковка координат, выбор слоёв маршрута, вид значков, подписи причин, приоритет подписей, фильтр по маршрутам оператора и формат его настроек.
- `build` собирает `consumer/static/{app.js,app.css,map-worker.js}`. Bundles вручную не правятся. Чтобы consumer раздал новую сборку, выполните команду запуска из [runbook](../docs/runbooks/local-demo.md#запуск-и-перезапуск-одна-команда).
- `check:browser` (Playwright Chromium, 1920×1080) — против запущенного стека на `UI_URL`. Проходы `live` не подменяют запросы и берут ожидаемые значения из того же API. Проходы `regression` явно подписаны и подменяют только `/api/snapshot` и `/api/route` (и `/map/moscow.pmtiles` для проверки недоступной карты), чтобы получить состояния, которые нельзя вызвать по требованию: `waiting_driver`, смена `run_id`, Backend offline, плохие координаты, коды причин, M1 на фиксированных данных. Regression-проходы не являются evidence живой цепочки. `UI_EVIDENCE_DIR=<абсолютный каталог>` сохраняет скриншоты, `UI_LIVE_EVENT_WAIT_S=90` ждёт реального предупреждения для M1 на live. Внешние запросы, page errors и console errors считаются провалом.

## Происхождение геоосновы

Локальный PMTiles v3, MVT (слои `earth`, `water`, `landuse`, `roads`, `buildings`, `boundaries` и другие), bbox 37.25,55.50,38.00,56.00, zoom 0–13. Из Protomaps basemap `https://build.protomaps.com/20260925.pmtiles`, OSM replication time **2026-09-25T04:00:00Z**, источник OSM/ODbL (© OpenStreetMap contributors); metadata и sha256 находятся в `consumer/map/manifest.json` и видны в «Диагностике». Это **геометрия OSM**, а не маршрут автобуса. Подписей улиц нет: шрифтовые glyphs не поставляются. Воспроизводимая команда с go-pmtiles v1.31.2:

```sh
pmtiles extract https://build.protomaps.com/20260925.pmtiles consumer/map/moscow.pmtiles --bbox=37.25,55.50,38.00,56.00 --minzoom=0 --maxzoom=13
shasum -a 256 consumer/map/moscow.pmtiles
```

Все JS, CSS, worker и плитки раздаёт consumer по localhost; внешних запросов нет. `/map/moscow.pmtiles` поддерживает HTTP Range.
